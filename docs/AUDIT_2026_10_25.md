## B011 – minimaler echter Durchstich, nur spezifiziert

**Zielkandidat:** Einen Song erfassen, lokal speichern, nach Serverneustart
erneut öffnen und denselben Inhalt lesen. Erstes spätere Produktstück:
semantisches HTML-Formular → lokales HTTP/API → Validierung/Anwendungsfall →
SQLite-Transaktion → neue Leseanfrage → wiederhergestellter Editorzustand.
Der Entwurf nutzt den vorhandenen `song_request`-/`song_response`-Vertrag;
keine zweite API oder konkurrierende Speicherimplementierung.

| Prüfschritt | Reproduzierbare Testvorgabe | Erwartung |
|---|---|---|
| Positiver Weg | synthetischer Song `probe-song-001`, Titel `Probe`, zwei Textabschnitte, Revision 0, feste Request-ID | neue Revision, nach Neustart byte-/inhaltstreu lesbar |
| Validierung | leere/zu große Felder und unbekannte Request-Felder | 400/413 mit Hilfe, ohne Datenmutation |
| Konflikt | zwei Clients mit derselben erwarteten alten Revision | einer speichert, anderer erhält 409; kein stilles Überschreiben |
| Unterbrechung | Fehler zwischen Beginn und Commit im isolierten Test | Rollback; alter Inhalt nach Neustart intakt |
| Bedienung | Tastatur, 200-%-Zoom, Abbrechen, nicht gespeicherter Entwurf | sichtbarer Zustand, Fokusführung, Entwurf geschützt |
| Schutz | Server auf `127.0.0.1`, Daten außerhalb Git, temporäres Testprofil | keine Netzfreigabe, keine echten Nutzerdaten |

**Umgebung:** später frisches Kubuntu/Linux-Testprofil, Python 3.12 und
versionierte Testabhängigkeiten, temporäre SQLite-Datenbank und isolierter
Testdatenordner. Keine persönlichen Songs, Logins oder echten Backups.
**Aufwand/Kosten:** ein begrenzter vertikaler Implementierungsscope plus
separates API-/Persistenz-/Browser-E2E-/Fehlerpaket; genaue Stunden und

echte Laufprotokolle, nicht die hier getesteten Planfälle.
